## (c2) Status-colour contrast audit (added in revision 2)

Reason: the first draft accepted green, amber, yellow and blue status colours as exceptions because no success, warning or info tokens exist. Bob and Charlie found several with too little dark-theme contrast, so every R3 exception (114 hits) was checked.

**Method.** A script computes WCAG 2.x contrast ratios (4.5:1 for text, 3:1 for graphics). Palette hex values are Tailwind v3's defaults (both apps extend the palette, not replace it; checked in each `tailwind.config.ts`). Surface colours are read from each app's `globals.css` (identical in web and admin): light `--background` and `--card`; dark `--background`, `--card` and `--popover`, taking the worst. A class pair on one line (a `bg-X` with a `text-Y`) is a fixed pair and is measured as written; a bare `text-Y` is measured against the theme surfaces; `dark:` and `hover:` variants are honoured. Lines where the colours sit on different lines (12 cases) were read in context by hand.

**Result for the 114 R3 exceptions:** 53 pass by script, 6 pass after a manual read, **55 fail and move to DEFERRED (PR 5a)**.

| Failing set                                                                                                                                                           | hits |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---: |
| Bare status text, fails in **dark** only                                                                                                                              |   19 |
| Bare status text, fails in **light** only                                                                                                                             |   24 |
| Fails in both themes                                                                                                                                                  |    6 |
| Manual cases that fail: 4 success/pending icon medallions (2.07 to 2.18:1, graphics need 3:1); `text-white` on `bg-green-600` (3.30:1) and on `bg-amber-600` (3.19:1) |    6 |

The three examples named in review all fail: `account/orders/[orderId]/page.tsx:69` and `checkout/_form.tsx:235` (`text-green-700`, 3.25:1 in dark), and `seller/dashboard/subscriptions/page.tsx:132` (`text-amber-700`, 3.25:1 in dark). The light-only failures (such as `text-green-600` on white at 3.30:1) were moved too, because contrast must pass in both themes.

**What remains EXCEPTION (59 R3 hits):** fixed `bg-X text-Y` pairs on one line, which stay readable in both themes. The thinnest are 4.51:1 (`text-amber-700` on `bg-amber-100`) and 4.52:1 (`text-orange-700` on `bg-orange-100`); the typical pair is 4.6 to 8.0:1. This includes the toasts, the status pills and the sidebar. The scrim `bg-gray-900/20` in `nav-bar.tsx` is decorative, not text.

**PR 5a re-triage.** Every one of these 59 remaining exceptions, and every deferred contrast entry, is re-triaged by PR 5a if it adds `success`, `warning` or `info` tokens or `Badge` variants: matching pairs move to the tokens and their exception entries are removed (a stale entry fails the audit, so none can linger).

**Limits.** Computed, not photographed: no dark-theme screenshots were taken for this audit. Border and ring colours, and decorative icons beyond the four medallions, were not measured. Ratios assume the default 16 px root.
